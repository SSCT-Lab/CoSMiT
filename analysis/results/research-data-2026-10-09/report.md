# research-data/2026-09-17 指标分析

分析日期：2026-10-09。机器可读结果见同目录 `metrics.json`，逐候选结果见 `candidate-methods.json`。本次分析读取已有导出，不重新调用模型或运行深度学习框架。

## 1. 范围与计数单位

主分析仅包含 discovery 和 unseen 两部分，排除已被驳斥的 D0028，并排除历史 controls。未使用 datasets 下的数据。补充模型与 TensorScope 记录单列，不加入主分析的候选数。

| 分区 | 候选数 | 家族数 | 候选内输入数合计 | 成对执行次数 |
| --- | ---: | ---: | ---: | ---: |
| discovery | 68 | 23 | 4,352 | 13,056 |
| unseen | 12 | 6 | 768 | 2,304 |
| 合计 | 80 | 29 | 5,120 | 15,360 |

每个候选有 64 个输入，每个输入重复 3 次。一条成对执行包含源和目标框架两次执行，因此对应 30,720 次单框架执行；重复执行不能算成独立候选。方向分布为 PyTorch→TensorFlow 33 个、TensorFlow→PyTorch 47 个。记录中的运行版本为 TensorFlow 2.20.0、PyTorch 2.9.1、NumPy 2.1.3。

指标分母必须区分：候选级方法结果以 80 为分母；单个模型请求类型以 80 为分母；五种请求的总体可用率以 400 为分母；执行级统计以 15,360 为分母。总体请求可用率按请求计权，不能直接作为各方法总体能力排名。

自测试通过和目标绑定被观察到的候选均为 80。上述通过计数来自记录；本次核对了执行标识的完整性、重复稳定性以及条款观察与执行观察的一致性，没有独立重算所有 API 的数学参考语义。

## 3. 模型请求可用率

可用率 = 返回可解析结构化结果的逻辑请求数 / 计划逻辑请求数。返回否定判断也算可用，结果是否正确另外评价。

| 请求类型 | 主请求可用数 / 80 | 主请求可用率 | 重试视图可用率 | 格式敏感性视图可用率 |
| --- | ---: | ---: | ---: | ---: |
| Direct LLM | 12 | 15.00% | 17.50% | 21.25% |
| Trace LLM | 0 | 0.00% | 0.00% | 0.00% |
| IntentTester：源端 TDL | 76 | 95.00% | 97.50% | 95.00% |
| IntentTester：目标 API | 75 | 93.75% | 97.50% | 93.75% |
| 目标端 TDL 扩展 | 76 | 95.00% | 97.50% | 95.00% |
| 全部 400 个逻辑请求 | 239 | 59.75% | 62.00% | 61.00% |

主请求失败率为 161/400 = 40.25%。discovery 可用率为 198/340 = 58.24%，unseen 为 41/60 = 68.33%。其中 Direct LLM 分别为 6/68 = 8.82% 和 6/12 = 50.00%；分区规模与家族构成不同，不能据此直接推出泛化改善。

按 29 个家族等权计算，五类主请求的宏平均可用率依次为 16.67%、0%、95.69%、92.53%、94.83%。不将家族内多个候选当作相互独立的证据来计算显著性。

### 候选级方法判断

| 方法 | 接受／支持 | 否定判断 | 失败或未决 |
| --- | ---: | ---: | ---: |
| Direct LLM | 11（13.75%） | 1（1.25%，invalid-assumption） | 68（85.00%，失败） |
| Trace LLM | 0 | 0 | 80（100%，失败） |
| IntentTester verifier-port | 66（82.50%） | 7（8.75%） | 7（8.75%，未决） |
| IntentTester + 目标 TDL 扩展 | 65（81.25%） | 8（10.00%） | 7（8.75%，未决） |

IntentTester verifier-port 联合源 TDL 与目标 API 两个检查；扩展方法联合三个检查。遵循现有实现：任一明确 false 即拒绝；全部 true 才接受；否则未决。因此，存在请求失败的候选仍可能因另一检查明确 false 而得到拒绝结果。不能用目标 TDL 单项的通过率代替扩展方法的总体接受率。

重试后 verifier-port 为 69 接受、7 拒绝、4 未决；扩展方法为 68 接受、8 拒绝、4 未决。接受率和确定判断率都不等于准确率。

## 4. 请求失败、重试与解析敏感性

主请求失败类型为 RuntimeError 75 次、RejectedResponse 56 次、URLError 21 次、JSONDecodeError 5 次、TimeoutError 4 次，共 161 次。Trace LLM 的 80 次失败包括 75 次 RuntimeError 和 5 次 URLError。现有错误类型不足以确定全部根因，更不能将请求失败解释为判断错误或方法本身无效。

25 次额外物理重试恢复 9 个逻辑请求，可用率增加 2.25 个百分点；在实际重试的请求中恢复率为 9/25 = 36%。这不是对全部 161 个失败请求进行统一重试得到的成功率。

格式敏感性视图不新增模型调用，恢复 5 个 Direct LLM 请求，使总体可用率增加 1.25 个百分点。导出只保留恢复状态，缺少对应语义判断，故不计算该视图的接受／拒绝分布。重试和格式敏感性是两个独立视图，恢复数量不能直接相加。

## 7. 对 RQs 的支持与下一步

| 问题 | 当前可以报告 | 尚缺的关键证据 |
| --- | --- | --- |
| RQ1：检出错误迁移并控制误拒绝 | 有限输入上的行为支持、模型可用率、判断分歧、失败类型 | 独立标注的正确／错误迁移；尤其是真实有效的违反案例；据此计算 precision、recall、F1、误拒绝率 |
| RQ2：条款引导探测效率 | 当前执行规模与重复稳定性 | 同一候选、同一预算下的策略对照；首次稳定反例所需探测数／耗时；未检出的预算耗尽记录 |
| RQ3：原因诊断与有效条件恢复 | 可供复核的 8 个分歧候选 | 独立原因和条件标注、诊断结果、条件发现与独立验证集上的结果 |

优先复核上述 8 个分歧候选，为每个候选记录“原断言→意图→适用前提→迁移断言→争议点→独立判定→可执行证据”。随后补充经确认的违反实例和正确迁移对照。完成这些后才能对主张中的“测试意图保持验证”开展正确性评价。

Docter 的导出缺少可按候选追溯的约束判断，无法安全剔除 D0028 后重算其结果；因此本报告没有用旧聚合矩阵拼出该方法的比较数值。需补充逐候选结果后再纳入。

## 8. 审计与复现

分析脚本：`benchmark/baselines/analyze_research_export.py`。在项目根目录使用 Python 运行以下命令，输出目录必须尚不存在：

```powershell
python benchmark/baselines/analyze_research_export.py research-data/2026-09-17 artifacts/analysis/research-data-rerun
```

脚本生成指标、逐候选结果、导出完整性和输入哈希四份 JSON。报告为对这些结果的人工整理。

导出清单中 3 个文件字节哈希直接匹配；32 个文本文件在 CRLF→LF 规范化后匹配，没有无法解释的差异。原始字节哈希另存于 `input-hashes.json`。检查了候选×输入×重复标识的完整覆盖、主请求的候选×类型覆盖、重试与原请求的身份和提示哈希，以及重试视图与请求日志的一致性。

指标定义和流程依据：`benchmark/baselines/summarize_experiment.py`、`verification_ports.py`、`experiment_worker.py`、`export_public_results.py`；研究问题及实验背景参照 `docs/research-remaining-tasks.md`、`experiment-procedure-2026-09-16.md`、`dataset-collection-2026-09-17.md`、`full-experiment-status.md`。文档中的旧结论不作为独立真实标签。
